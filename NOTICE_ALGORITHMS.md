# Algorithm citations

Standing rule (`BUILD_PLAN_V2.md` #3): every algorithm gets a citation here.
Implementing a published method from its description is expected; copying
code from any existing solver is not — not once, not anywhere.

| Component | Algorithm | Citation | Status |
|---|---|---|---|
| `simplex/dense_simplex.*` | Two-phase bounded-variable primal simplex, dense tableau, Bland's rule anti-cycling | Standard method — see e.g. Bazaraa, Jarvis & Sherali, *Linear Programming and Network Flows*, ch. 4 (bounded variables); Bland, "New finite pivoting rules for the simplex method," *Math. of OR* 2(2), 1977 | **Throwaway** — Phase 1.1 proof-of-life only, to be deleted once Phase 2.1's revised simplex passes Checkpoint 2.1. Not intended to survive the project. |
| `io/mps_reader.*` | MPS free-form parsing, with a strict fixed-column fallback | Format only, not an algorithm — no citation needed. Netlib RANGES-section sign convention and the fixed-column field layout (columns 2-3/5-12/15-22/25-36/40-47/50-61) follow the description in Maros, *Computational Techniques of the Simplex Method*, App. B | Permanent |
| `checker/checker.*` | Primal/dual residual and complementarity-gap computation | Standard LP optimality (KKT) conditions — see e.g. Nocedal & Wright, *Numerical Optimization*, ch. 12 | Permanent |
| `la/scaling.*` | Geometric-mean scaling + infinity-norm equilibration | Suhl & Suhl 1990, "A fast LU update for linear programming" | Permanent |
| `la/markowitz_lu.*` | Markowitz-count pivot selection with threshold partial pivoting; reports which columns/rows it could not pivot on failure (`SingularityInfo`), for basis repair | Markowitz, "The elimination form of the inverse and its application to linear programming," *Management Science* 3(3), 1957; threshold pivoting and elimination bookkeeping per Suhl & Suhl 1990 | Permanent. **Count-bucketed pivot search**, landed together with the refactorization-interval change below — the two only work as a pair. The original search rescanned every active column at every elimination step (O(m·nnz)); component timing showed that at 77% of pilot87's entire solve, ~0.38s per factorization. This is the standard count-bucketed search (the bookkeeping half of Suhl & Suhl): columns are filed by current nonzero count, the search examines only the sparsest 64, and it falls back to the exhaustive scan whenever none of them yields a threshold-acceptable pivot — so singularity detection stays exact and the bound can only ever cost fill quality, never correctness. **It was implemented, measured, reverted, and then re-landed**, which is the part worth recording: on its own it was 2.08x faster but cost `pilot87` (84/93 → 83/93), and widening the search did not recover it. The reason was not search width. Making factorization ~5x cheaper changes what the *right refactorization interval* is — with a cheap rebuild you should rebuild more often and keep the eta chain short — so the fix was to retune that interval at the same time (m/10 → m/20). Together: **84/93 with all 84 verified instances solving in 63.5s total**, where the same score previously took ~93s; `pilot87` 56.9s → 14.9s, `degen3` 45.6s → 12.0s, `fit2p` 46.3s → 7.6s. `pilot87` in particular is no longer inside the 60s cap by 3 seconds — it now clears it by 45. |
| `la/lu_solve.*` | Gilbert-Peierls sparse triangular solve (DFS reachability) | Gilbert & Peierls, "Sparse partial pivoting in time proportional to arithmetic operations," *SIAM J. Sci. Stat. Comput.* 9(5), 1988 | Permanent |
| `la/basis_factorization.*` | Product-form-of-the-inverse (PFI) eta update, **not** Forrest-Tomlin | Classical technique — see e.g. Maros, *Computational Techniques of the Simplex Method*, ch. 3. **This is a deliberate, documented substitution**: BUILD_PLAN_V2.md's Phase 1.2 checklist names Forrest & Tomlin 1972's LU-form bump/Hessenberg update specifically. That algorithm's exact permutation-and-elimination procedure was judged too easy to get subtly wrong from memory without a reference to check against, so the simpler, fully-rederived PFI eta update was implemented instead, paired with a refactorization policy to bound the eta-chain growth PFI alone doesn't guarantee against the way true Forrest-Tomlin does. See the file header comment. | Interim — upgrading to true Forrest-Tomlin is tracked, not done |
| `simplex/revised_simplex.*` | Bounded-variable primal revised simplex; a greedy weighted-matching crash basis; Devex pricing (with a tiny deterministic per-column tie-breaking perturbation, and a Bland's-rule fallback after sustained degenerate pivots); a Harris two-pass ratio test with adaptive tolerance expansion; geometric-mean scaling (`la/scaling.*`) applied around the whole solve; **singular-basis repair with phase restart** | Bazaraa, Jarvis & Sherali, *Linear Programming and Network Flows*, ch. 7 (revised simplex, bounded variables); Harris, "Pivot selection methods of the Devex LP code," *Math. Programming* 5, 1973 (Devex weights, and the same paper's motivation for the two-pass ratio-test structure used here — not its full bound-relaxation machinery); Bland 1977 (anti-cycling fallback); crash bases are standard practice (see e.g. Maros, *Computational Techniques of the Simplex Method*, ch. 3) — this one is a from-scratch greedy largest-coefficient-first matching, not a specific named published variant | Permanent — this is the real solve path, not throwaway. No steepest-edge or full Harris bound relaxation yet — see file header. **Measured honestly across five increments** on the Netlib set: Dantzig alone 72/93; +Devex 71/93 (net neutral — fixed 4, regressed 5, big per-instance wins like d2q06c's 117786→12880 iterations, but no fix for the underlying ill-conditioning risk); +scaling (which existed since Phase 1.2 but was never actually wired into any solve path until this) 74/93 with **zero** checker-rejected "optimal" claims, versus 1 before; +crash basis 76/93, zero checker-rejected claims — fixed `grow15`/`grow22` (previously `NUMERICAL_ERROR`), regressed `pilotnov` similarly and turned two others (`bore3d`, `brandy`) from converging into `ITERATION_LIMIT`; +perturbed Devex tie-breaking (see the "cost perturbation" note below — this is a deliberately safer variant of the checklist item, not the textbook one) **80/93 with `--presolve` on**, zero checker-rejected claims, down to just 4 non-converging instances (`pilot87`, `scsd1`, `scsd8` numerical error; `tuff` iteration limit) — from 18 at session start. Scaling attacked the actual root cause (an unscaled matrix amplifying through elimination) rather than only the symptom two earlier defensive checks (`MaxBoundViolation`, before trusting an unbounded *or* optimal conclusion) were added to catch. **Cost perturbation, deliberately NOT the textbook form**: perturbing the objective ITSELF requires certifying the perturbation is smaller than the smallest possible gap between two distinct vertices' true objective values — no principled way to guarantee that for an arbitrary Netlib instance, and getting it wrong means silently reporting a suboptimal vertex as optimal. Implemented instead: a tiny (1e-9 relative), fixed, deterministic per-column factor applied ONLY to the Devex tie-breaking score — never to the reduced cost used to decide whether a direction improves, never to the ratio test's bound targets — so it can change which of several EQUALLY-improving directions is tried first, but can never turn a correct optimum into a wrong one. Bland's-rule fallback already gives proven, zero-risk anti-cycling termination on its own; this addresses the separate problem of grinding through more degenerate pivots than necessary before that threshold is even reached. See `PerturbationFactor`'s comment in the file for the full argument. **Singular-basis repair (+1, and it retires the whole `NUMERICAL_ERROR` category)**: all three remaining numerical failures — `scsd1`, `scsd8`, `pilot87` — turned out to die at one single line, a mid-solve refactorization declaring the basis singular after thousands of otherwise-healthy iterations. `la/markowitz_lu.*` now reports which columns it could not pivot and which rows were left uncovered; `RepairSingularBasis` swaps exactly those basis columns for the slacks of the uncovered rows, which is provably nonsingular (the already-pivoted part is triangularizable by construction, and the unit replacements cover precisely the missing rows), and the solve continues instead of being abandoned. A repair legitimately MOVES the current point, which invalidates phase 2's assumption that it starts from the feasible point phase 1 handed it — so the driver restarts the two-phase sequence from the repaired basis (capped at 4 restarts) rather than reporting a failure that is really just "the point moved". Result: **81/93, zero checker-rejected claims, and zero `NUMERICAL_ERROR` instances** (from 3). `scsd1` (8.66667) and `scsd8` (905) now verify against their published optima; `pilot87` verifies too (301.71, checker PASS) but takes ~110s, over `bench/run_netlib.py`'s 60s per-instance cap, so it scores as `TIMEOUT` — every one of the 12 remaining non-verified instances is now a time/iteration budget issue, not a correctness failure. **Performance (+1.57x, no score change)**: profiling a hard instance put ~54% of the whole solve in the Devex weight update, which computed the tableau's pivot row by dotting every nonbasic column against a dense `rho` through a helper returning a `std::vector` by value — a heap allocation per nonbasic column per pivot. Rewritten to scatter `rho`'s nonzeros through a row-major view of A built once per solve; identical arithmetic, verified by every instance returning the same objective AND the same iteration count. Total time over the 81 verified instances 163.6s → 104.2s; `fit2d` 23.3s → 3.8s, `scsd8` 2.8s → 0.8s. The same trick was then considered for the pricing loop and **rejected on measurement**: `rho` is a BTRAN of a unit vector and genuinely sparse, but `y` is a BTRAN of the cost vector and measured 55–69% dense and rising, so scattering would have bought little while perturbing pivot paths through changed floating-point summation order. What remains is an iteration-count problem, not a per-iteration-cost one — steepest-edge pricing is the lever that addresses it. **Harris ratio test with adaptive tolerance expansion (+7, 84/93 → 91/93)**: pass 1 measures against bounds relaxed by a delta so a variable already on its bound still admits a strictly positive step — the degenerate case, where the strict minimum ratio is 0 for many rows at once and the solve stalls; pass 2 then takes the largest \|rate\| among everything that relaxed limit admits. The delta is adaptive because a flat one is wrong at both ends, measured: at 0.1x the feasibility tolerance it is too small to break a stall (`tuff` burned its whole iteration budget), at a flat 1.0x `tuff` solves in 0.014s but `degen3` and `modszk1` fail numerically. It therefore sits at the small base while pivots make progress and ramps toward the full tolerance as degenerate pivots accumulate, collapsing back on the first real step (the classic EXPAND idea). Crucially the expansion is **strictly non-losing**: at a ramp ceiling of 5 `degen3` reported UNBOUNDED — a wrong answer the checker cannot catch, since it only validates claimed optima — so any attempt ending in numerical error, unboundedness or an iteration limit now redoes the whole solve from scratch with the expansion off. From scratch matters: an in-place phase restart carries the damaged basis forward and left `scsd8` still failing. Result: **91/93 verified in 61.3s total, zero checker-rejected claims, zero numerical errors**, only `dfl001` and `greenbea` left, both TIMEOUT. |
| `presolve/presolve.*` | Fixed-variable substitution, empty-column removal, redundant-row removal, singleton-row bound-tightening-then-removal, and free-column-singleton substitution, to a fixpoint | Standard presolve reductions — see e.g. Andersen & Andersen, "Presolving in linear programming," *Math. Programming* 71, 1995 | Partial, but substantially wider than before — three row-removing reductions added this session (redundant row, singleton row, free column singleton), each with its own postsolve dual/primal recovery rule (derivations in the file header). Forcing rows, dominated-column/dual-fixing, duplicate row/column detection, coefficient tightening, and general (non-removing) bound tightening are still not implemented — the last was tried and deliberately reverted: it's sound for feasibility but breaks the checker, because narrowing a column's bound without a postsolve record leaves the checker (which validates against the ORIGINAL bounds) unable to tell a synthetic tightened bound from the variable's real one; fixing that for a row that stays active and has other columns depending on its dual is a harder problem than this pass takes on, same class of issue as forcing rows. **Measured on the full Netlib set** (`--presolve`, opt-in): 76/93 verified, **zero** checker-rejected claims — the three additions were not a clean win in isolation (the first pass had four real bugs, each found only by the full-set run, not the smaller cross-check suite: dropping a substituted column's objective contribution entirely — capri's objective came out wrong; losing the existing empty-row infeasibility check when it was folded into the new redundant-row logic; a primal-reconstruction bug where two free-column-singletons chained forward instead of the needed reverse order — capri/vtp.base failed the checker; and a double-counting bug where postsolve re-summed a row's already-fixed columns that presolve had already folded into the substitution's RHS — greenbeb's postsolved solution was primal-infeasible by ~10^4). All four are fixed and the full set passes clean. Net effect vs. the two-reduction baseline (77/93): fixed `greenbeb` (was `ITERATION_LIMIT` even after 1158s *without* presolve — 8s and verified *with* it) and `pilotnov`, but introduced `maros` and `perold` as new `NUMERICAL_ERROR`s — a small problem-size change appears to trip `revised_simplex.cpp`'s pre-existing numerical fragility differently, not a new soundness bug (confirmed no checker-rejected claims either way, and the reduced matrices' coefficient ranges are unchanged from the original). Left opt-in rather than promoted to default, per BUILD_PLAN_V2.md's on/off-equivalence standing rule and the still-incomplete reduction set. |
| `simplex/dual_simplex.*` | Bounded-variable dual simplex: most-infeasible leaving-row selection, a dual ratio test on the pivot row, Bland's-rule fallback after sustained degenerate pivots | Bazaraa, Jarvis & Sherali, *Linear Programming and Network Flows*, ch. 8 (dual simplex); Koberstein's dual simplex thesis, cited in BUILD_PLAN_V2.md's core reading list, for the canonical bounded-variable treatment; Bland 1977 (anti-cycling fallback) | Partial — **only problems with a trivial dual-feasible start are supported** (nonbasic structural columns placeable at whichever bound their objective sign requires; the all-slack basis is then immediately dual-feasible with zero extra work). A column whose favorable bound doesn't exist, or a free column with nonzero cost, has no such trivial start; the real fix is a composite/Big-M dual phase 1 mirroring what primal simplex's own phase 1 does for primal feasibility — not implemented. Reports `NUMERICAL_ERROR` in that case rather than a wrong answer. **Measured on the full Netlib set** (`--solver dual`): 35/93 verified (of the ~38 instances with a trivial start; the rest correctly report `NUMERICAL_ERROR` for lacking one), **zero** checker-rejected claims — that required two fixes found via full-set runs, not the smaller cross-check suite: a missing Bland's-rule fallback (root cause of an observed multi-minute hang) and a missing dual-feasibility re-verification before declaring optimal (dual feasibility is supposed to be an *invariant* every pivot maintains by construction, and nothing had ever re-checked that it actually held — 3 instances were reporting a confidently wrong "optimal" with large complementarity violations until this was added). Cross-validated against `SolveRevised` too (`tests/dual_simplex_test.cpp`) — meaningfully independent since the two algorithms pick entering/leaving variables in the opposite order. |

## Third-party tools (not solver code)

`bench/tools/emps.c` is fetched verbatim from https://www.netlib.org/lp/data/emps.c
to decode the Netlib LP archive's on-disk encoding into plain MPS text. It
performs no optimization, is never linked into `inferno_core` or `solver`,
and is a data-format utility, not a solver dependency. See
`bench/tools/NOTICE.md`.

**Exact steepest-edge pricing was attempted and reverted.** BUILD_PLAN_V2.md's pricing ladder ends at steepest edge, and the machinery was nearly all in place: the weight is gamma_j = ||B^-1 A_j||^2, whose exact per-pivot recurrence needs the pivot row (already scattered for Devex), the entering column's FTRAN (already computed) and one extra FTRAN for tau = B^-1 rho, with the update touching only the columns the scatter already identified. Implemented and measured: `25fv47` improved (1.2s → 0.64s), but `degen3` went 2.1s → 20.6s (58218 iterations) and `pilot87` 14.9s → over 90s. The cause is structural rather than a coding slip: the exact recurrence presumes the weights it is updating were themselves exact, and exact initialization costs one FTRAN **per column** — far more than the entire solve. Devex survives an approximate start precisely because it is not exact: it only ever grows a weight and periodically resets its reference framework, so bad values decay out. The exact recurrence has neither guard, so an approximate start propagates and compounds. Making it work needs a proper reference-framework reset scheme (or partial exact re-initialization), which is a larger piece of work than a recurrence swap. Reverted under the no-regression rule; recorded because the derivation and the cheap-tau observation are the reusable part.

**Duplicate-column merging was attempted and reverted.** The design
(merge two columns with an identical matrix column and identical
objective coefficient — genuinely common in Netlib: a full-set scan found
1943 such columns across 34 instances, sometimes heavily, e.g. `d6cube`
has 735) fired a lot, and a first pass fixed two real bugs found via the
full Netlib run (an ordering bug in how the merged value was split back —
other reductions on the same representative column needed the still-
merged pooled value, not the post-split share). But fixing those surfaced
a THIRD, deeper one: a column later merged away could have been
referenced earlier (in application order) by a completely different
row's free-column-singleton substitution, needing that column's
INDIVIDUAL final value at a point in postsolve before the merge split
had run — and unlike the two-reduction interactions already handled
elsewhere in this file, resolving this one correctly means unifying two
separate dependency-resolution passes (the primal free-column-singleton
reverse walk and the later dual-recovery fixpoint) into one, rather than
adding another isolated special case. Given the standing "zero
checker-rejected claims" rule and that a clean, fully-verified state
already existed one commit prior, the responsible call was to revert
rather than ship a plausible-looking fix without confidence it was the
last bug in the chain. Tracked here as real, attempted, not-done — not
silently dropped.
